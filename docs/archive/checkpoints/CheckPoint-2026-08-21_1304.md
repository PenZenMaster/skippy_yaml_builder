# Checkpoint - 2026-08-21_1304

## Context summary

This session's work on Skippy came out of a parallel effort on
`rr_yacss_factory` (a Node/TypeScript CLI driving the YACSS REST API in
bulk). That project's user asked whether Skippy's client YAML output
could feed rr_yacss_factory directly. Investigation found Skippy's
current form (a simple manual client-intake form: name, contact, address,
target cities, services, FAQ, etc.) captures everything about *who the
client is*, but nothing about *how to build their site in YACSS*
(template, cloud account targeting, tier/page structure, AI generation
settings, bucket naming). The user asked for a new `yacss:`-equivalent
section to be added to Skippy's form to carry that missing build-mechanics
data, using United Structural Systems as the reference client.

## Accomplishments

- Added 11 new fields to `main.py`'s form, all prefixed `"YACSS "` so
  they're visually grouped separately from the existing client-profile
  fields: Build Type, Template, Bucket Keyword, Cloud Account IDs (comma
  separated), Tier0 Pages, Tiers (tier:pages, one per line), AI Platform,
  AI Model, Tone, Language, Items Per Listicle.
- Added placeholder hints (`self.placeholders` dict, applied in the
  existing grid-layout loops) for the new fields only, since their valid
  values aren't self-evident the way "Phone" or "Email" are.
- Wrapped the whole form in a `QScrollArea` -- the new fields pushed the
  right column from 12 to 23 items, which no longer fit the fixed
  800px-tall window. `load_yaml()`/`save_yaml()` needed no changes: both
  are already generic over `self.inputs`' keys.
- Verified via an offscreen `QApplication` (`QT_QPA_PLATFORM=offscreen`)
  smoke test (not committed, deleted after use): the app compiles and
  launches without error, and a save/load roundtrip with real values in
  the new fields serializes in the same flat-key YAML style as the rest
  of the form (confirmed against `client_yaml/united_structural_systems`'s
  real, current-format output).
- Committed as `c6779f2 feat: add YACSS build-settings section for
  rr_yacss_factory integration`.

## Technical changes (files)

- `main.py` -- `self.inputs` dict gained the 11 new `QLineEdit`/`QTextEdit`
  entries; new `self.placeholders` dict; both grid-layout loops
  (`for i, key in enumerate(left/right)`) gained a
  `widget.setPlaceholderText(...)` call when a placeholder exists for that
  key; `central_widget` is now wrapped in a `QScrollArea` set as the real
  central widget, rather than being the central widget directly.

## Known issues

- `main.py`'s `save_yaml()` never splits the "one per line" text fields
  (Target Cities, Services, Social/Citation URLs, FAQ Questions) into
  lists -- it writes the raw multi-line string as-is (`toPlainText()`),
  matching the *current* format seen in the real
  `united-structural-systems.yaml` file. Any downstream consumer (e.g.
  rr_yacss_factory) needs to split on newlines itself; this was already
  true before this session's changes and was not altered.
- No validation was added on the new YACSS fields (e.g. that "Tiers" lines
  actually match a `tier:pages` pattern, or that "Cloud Account IDs" is
  non-empty) -- they're plain text fields like the rest of the form, left
  to whoever consumes the YAML to validate.
- The new fields were designed against rr_yacss_factory's job schema as it
  stood 2026-08-21 (`ListicleJob`/`CloudStackJob` in that project's
  `src/jobs/types.ts`). That project has since also added a third job type
  (`masspage`, Silo-mode "AI Website" sites) in the same session, with its
  own build-mechanics needs (Silo builder mode, AI platform, page titles)
  that don't yet have a place in this form. Not addressed this session --
  flagged for whoever next reconciles the two projects' schemas.

## Next session priorities

1. If rr_yacss_factory's `masspage` job type gets its content-generation
   gap fixed and becomes a real target, revisit whether this form needs
   additional YACSS fields for it (Silo sub-mode, page-title list, AI
   platform) beyond the generic ones added this session.
2. Consider whether the "one per line" text fields should actually be
   split into real YAML lists at save time, rather than left as raw
   multi-line strings -- would make downstream parsing (rr_yacss_factory
   or otherwise) simpler, at the cost of changing this tool's current
   on-disk format.
3. No actual United Structural Systems YACSS batch has been run through
   rr_yacss_factory yet using data sourced from this form -- that's the
   real end-to-end test this integration was for.
